HopOS · the Go-only OS

No kernel between your app and the hardware.

A ~15 MB signed image on a USB stick is the entire node. It boots a 128-core Ampere Altra, any other UEFI arm64 box, a Raspberry Pi, a Radxa Zero 3E or a €15 RISC-V board, and runs each Go app on its own physical cores, inside its own memory cage. Your core count is your headroom — one design, one job spec, from that €15 board to 127 caged app cores.

Security by subtraction

Meltdown, Spectre, MDS, container escapes — different bugs, one root: sharing. Linux must safely share everything between everyone, with mitigations that are partial, ongoing and expensive. HopOS takes the simpler road: share nothing by default. Cores and memory are handed out whole, and the cage is silicon — a second translation stage on ARM, a PMP whitelist on RISC-V — not kernel policy.

Attack classLinux answer (mitigation)HopOS answer (structure)
Meltdown-class: kernel leaks to userKPTI — unmap the kernel, mostlyNo kernel in the app’s address space at all. Behind the cage, the OS is not unmapped — it is unnameable.
SMT side channels (MDS family)Disable hyperthreading, scrub buffersNo involuntary co-tenancy — an attacker can never land on your core. Sharing is opt-in, among apps you name.
Spectre across processesFlush branch predictors on every context switchYour neighbour never runs on your core unless you put them there — an adversary can’t.
Container escapes (runc, Dirty Pipe, …)Patch treadmillNo containers, and no shared kernel to escape into.
~400 syscalls + ioctl jungleseccomp/AppArmor profiles you must writeAn ABI of ten operations, enforced by hardware, not policy.
Rogue DMA from a workloadIOMMU configuration, fingers crossedApps have zero MMIO. Only the node programs devices — USB included: a bus-master can’t be caged without an IOMMU, so HOP owns the xHCI controller and hands apps input events, never registers.

The double win: no mitigations tax. Apps run at the silicon’s spec clock — measured, not promised — because there is nothing to scrub. You don’t have to patch what you don’t share.

Safe by default, share when trusted. Everything above is the default: every app owns whole cores. When density matters more than a private core, you opt in — tag apps with a sharegroup and they cooperatively share a pool of whole cores you size yourself. You pick your own cage-mates, so an attacker still can’t get onto your core: the only apps sharing it are ones you grouped, that already trust each other. And even then the memory and network cage never softens — each app keeps its own hardware-bounded partition and its own network stack, so nothing bleeds between neighbours, and apps you don’t group keep the whole-core guarantee in full. It’s how a 4-core Pi runs a dozen trusted services, or a microservice fleet packs onto a handful of cores — without giving up hardware isolation between tenants.

One cage, two instruction sets. A cage does two separable things: it bounds what an app may reach — the invariant — and it relocates the app so every slot sees itself at the same address, which is only a convenience. On ARM one page table does both. The XuanTie C906 in a €15 RISC-V board has no hypervisor extension at all — stage-2 does not exist on that silicon — so there the bound is a PMP whitelist and the relocation a supervisor page table.

On both, the loader stub reads the cage configuration back and refuses to dispatch on a mismatch: a cage that cannot be shown to stand does not get an app. And because a hart reset hands back a provably clean slot, a kill is a reset.

Nothing lives on the node

HopOS is stateless — and so is HOP on top of it. The boot stick carries a signed image and six lines of config; jobs, app images and cluster state live in object storage and are fetched at boot. State on S3, not on metal — there is nothing on the machine to lose, corrupt, drift or steal.

That is the whole trick behind the power-cut number: pull the plug on 126 running jobs and the node rebuilds itself from S3 in 17.4 s. Lose the machine entirely? Move the stick to another box. “Reinstall” means re-imaging a USB stick. Even shared data is designed to be fetched, not owned.

An app that needs to keep something asks. Four of the ten ABI operations copy between a job’s own folder in the object store and its own file view — pull, push, list, drop. The node enforces the prefix, so an app cannot name anything outside its own folder, and it picks a name rather than a URL. Copies on demand, not a sync daemon: nothing promises persistence you did not ask for.

Small enough to actually read

Lines of code, excluding tests, comments and blanks — counted the way the compiler sees it, by a script that runs go list per release image. A file that only links for one instruction set or one board counts only there; example apps, probes and dev targets don’t ride along. If it isn’t in the image you boot, it isn’t in the number. The rung you have to trust is the first one; the board rung — its NIC, PHY and display drivers included — is a swappable outer shell, already outside every cage.

A Linux node doing the same job trusts GRUB, the kernel (~30,000,000 lines), systemd, libc and a container runtime. HopOS is the whole node — bootloader included — in ~10,800. No node ever links two boards or two instruction sets: whatever you boot is portable + one ISA + one board, so a node fits in a single AI context window and you can audit the machine you actually booted in one sitting, human or machine.

The board rung is where new hardware lands — the core stays put. Five boards so far and every one weighs in around those ~2,000 lines. Even the Radxa Zero 3E fits, and its firmware lights neither the NIC nor the HDMI connector: the GMAC and PHY sit in its board rung, the scanout in the GUI flavour — a headless image links zero graphics. Of the whole port, about fifty lines touched the portable core. Supporting a new board is a driver problem, not an OS problem.

HopOS does less. On purpose.

It runs Go applications, compiled for HopOS — no containers, no other languages, no general-purpose anything. That narrowness is where the isolation and the ~15 MB come from. Need Docker images or non-Go services? Run HOP with its exec and Docker drivers on a Linux box in the same cluster, and keep HopOS for the apps that deserve the metal.

Only Go? Mostly. On your own machine, GoNet runs .NET in pure Go on wazero, with no .NET runtime installed — an experiment, and the test suites of two production repos run green through it.

Slot apps that already exist

The infrastructure a node usually needs is built and published as signed slot images. Each one is an ordinary app in a cage — no privileges, no MMIO, the same rules as your own code. A job spec points at the URL.

welcome
A page on port 80 with what the node is running on: cores, RAM partition, architecture, uptime. Ships in the default headless config — http://<node-ip>/ is the install check. There is one running at demo.gethop.org.
cloudflared
Cloudflare’s own tunnel run, unmodified: a node behind NAT, with no inbound port and no kernel, reachable from the internet.
hoplb
Load balancer that takes its routes live from the cluster, streaming-safe for SSE and websockets.
hopdns
Cluster DNS, so a job can say display.hop.local instead of an address — with static CNAMEs and merged federation queries.
hopprom
Prometheus exporter with per-job CPU and memory — no agent and no node exporter, because the node already measures every slot.
SURF
Windows, a software compositor and a browser, built on the framebuffer grant. A separate thing that runs on HopOS, not part of it: the tech demo.

How much of the Go ecosystem compiles

cloudflared is the measurement rather than the feature. Its dependency tree — a forked quic-go, gopacket, gopsutil, gRPC, OpenTelemetry, Prometheus, capnproto — compiles for HopOS untouched, on two small platform fallbacks. The 30 MB arm64 image is somebody else’s program in a slot, on the same terms as yours.

They are published as signed artifacts in HOP’s rolling release, for both architectures where one exists. One job spec covers both: list two artifacts, each with a match on node.arch, and every node downloads the build that fits it.

You can load the €15 node right now: demo.gethop.org. It is one of the RISC-V boards, on a desk, behind NAT — two harts and 256 MB carrying the same isolation contract as the 128-core Altra: the app ABI is identical, only the silicon under the cage differs. Two apps cooperatively share its single app core — the tunnel that makes it reachable and the page that answers you — each in its own partition. The uptime counter on that page is the soak test.

Download

The quick road is the imager — burn, configure, update and find HopOS nodes: one window, no terminal. It fetches the newest signed release itself, writes and verifies in one pass, updates a card keeping its config, and FIND lists every node on your network — boot log included.

Boots by default. A fresh card is a working node — API open on purpose (hopos.insecure=1), warning on every boot until you give it a hopos.apikey. That is a deliberate first-boot trade: you secure a node you have seen work, instead of debugging a key and new hardware at the same time. Configuring and updating happen in place, config intact, without mounting anything — even on the LicheeRV, where the config lives inside the kernel.

Verify before you boot it. Every release is signed with an SSH key; allowed_signers and release_key.pub are published next to it.

 check the signature, then the images
$ ssh-keygen -Y verify -f allowed_signers -I hello@gethop.org \
      -n gethop-release -s SHA256SUMS.sig < SHA256SUMS
$ shasum -a 256 -c SHA256SUMS
hopos-uefi.img.gz: OK
