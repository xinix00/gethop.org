SURF · a tech demo

Windows that live in the cluster.

An app draws into an image.RGBA on whichever machine it happens to run on; a display node composites it as a window on one screen. Kill the machine behind a window, let HOP restart that app somewhere else, and the window comes back by itself. All of it is ordinary HopOS apps.

hop-os-surf on GitHub → what’s in it

this is a demo of what a HopOS app can be →

The window is not on the machine

On a normal desktop a window belongs to a process on that same box. Here it belongs to a job in a cluster. The app opens a window, draws, calls Present() — and if the connection breaks it reconnects and resends a full frame on its own. Nothing in the app knows or cares which machine the pixels end up on.

Two kinds of app. A pixel app ships frames: simple, and how the clock and the browser work. A scene app ships one binary widget tree once and then byte-sized patches — the display does layout, re-flow and hit-testing, and hands back semantic events. That is why a calculator keypress is a handful of bytes on the wire, and why the whole thing stays usable over a network instead of a video cable.

The compositor is software all the way down — no GPU driver exists anywhere in this stack. There is also a web-KVM: the display serves /kvm, so you watch that screen and drive mouse and keyboard from any browser, and /screen.png for a machine with no monitor at all.

A browser, written from scratch

Not a wrapper around someone else’s engine — there is none to wrap. Its own fetching, its own DOM, its own CSS cascade, its own layout and its own rendering, in a caged app with no operating system underneath it.

And somebody else’s emulator

goboy, a Game Boy emulator in pure Go, as a slot app with its screen in a SURF window — on the display node’s own monitor, with the node’s own USB keyboard and mouse since HopOS v1.10, or in a browser through the web-KVM. Upstream is neither forked nor pinned: a prepare script pulls the latest branch head and drops two additions beside it. Zero lines of upstream code changed — a constructor that takes the ROM as bytes, and an empty stand-in for the cgo audio package.

No sound — SURF has no audio channel, so the APU runs with its output disabled. And the window belongs to the cluster, not the machine: kill the node, let HOP restart the job elsewhere, and the window returns — at the title screen, since nothing hands over the save state.

What’s in the demo

Every one of these is a separate HopOS job you can start, kill and move independently — including the desktop chrome itself.

display
The surface: SURF sessions, the software compositor, the taskbar and start menu, and the web-KVM. The only app that touches the framebuffer.
launcher
The desktop starting itself: buttons come from the node’s boot-config app catalog, and a click submits that job to HOP.
taskman
The cluster watching itself — agents → jobs → tasks → live logs over SSE, each log line one patch on the wire.
browser
Own DOM, cascade, layout and rendering. Slow, incomplete, and it renders real pages.
clock · calc
The two smallest examples, one of each kind: a pixel app that draws an analog face, a scene app whose keypad lives display-side.
dash
The honest one: a dashboard that measures and shows its own wire traffic, so the protocol claims are checkable.
goboy
A ported Game Boy emulator — above. The first port of third-party GUI software, and the pattern for the next one.

Limits

A tech demo: not supported, not versioned for you, not run in production. The published images are arm64 only and need HopOS v1.5.1 or newer, parts of the on-screen text are still Dutch, and the browser fails on plenty of the web.

What it is not is a change to HopOS. Graphics in the OS is one grant — it hands one app the framebuffer — and it lives in the GUI flavour: a headless image links none of it. Windowing, compositing, the browser and every app above live in their own repo and are cageable, killable and replaceable like any other job. A desktop cost the operating system nothing.

The two things this is built on. HopOS gives every app whole cores behind a hardware cage; HOP decides which machine each app runs on — and moves it when a machine dies, which is why a window can outlive its node.
